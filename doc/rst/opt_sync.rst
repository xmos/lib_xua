Synchronisation
===============

The codebase supports asynchronous, synchronous and adaptive USB transfer modes as defined by the
USB specification(s).

.. note::

   The selection of synchronisation mode is done at build time and cannot be changed dynamically.

Asynchronous mode (``XUA_SYNCMODE_ASYNC``) has the advantage that the device is clock-master. This means that
a high-quality local master-clock source can be utilised. It also has the benefit that the device may
synchronise its master clock to an external digital input stream e.g. S/PDIF and thus avoiding sample-rate
conversion.

The drawback of this mode is that it burdens the host with syncing to the device which some hosts
may not support. This is especially pertinent to embedded hosts, however, most PCs and mobile devices
will indeed support this mode.

Synchronous mode (``XUA_SYNCMODE_SYNC``) is an option if the target host does not support asynchronous mode
or if it is desirable to synchronise many devices to a single host.

Adaptive mode (``XUA_SYNCMODE_ADAPT``) is a further option for hosts that do not support asynchronous mode.
The device follows the rate at which the host actually delivers audio samples, rather than the USB
start-of-frame (SOF) rate.

In both synchronous and adaptive modes the host, not the device, sets the audio rate, so the device
must generate a master clock that tracks it (see :ref:`opt_sync_mclk_recovery`). Input from external
digital streams, such as S/PDIF or ADAT, is not supported in either mode, since that would require
sample-rate conversion between the digital stream and the USB host clock domains.

Setting the synchronisation mode of the device is done using the defines in :numref:`opt_sync_defines`.

.. _opt_sync_defines:

.. list-table:: Sync mode
   :header-rows: 1
   :widths: 25 60 20

   * - Define
     - Description
     - Default
   * - ``XUA_SYNCMODE``
     - USB synchronisation mode: ``XUA_SYNCMODE_ASYNC``, ``XUA_SYNCMODE_SYNC`` or ``XUA_SYNCMODE_ADAPT``
     - ``XUA_SYNCMODE_ASYNC``
   * - ``XUA_USE_SW_PLL``
     - Use the `xcore.ai` secondary PLL and `lib_sw_pll <https://www.xmos.com/file/lib_sw_pll>`__ to
       generate the master clock. Must be 1 for adaptive mode.
     - 1 (enabled) for `xcore.ai` targets

.. _opt_sync_mclk_recovery:

Master clock recovery
---------------------

In synchronous and adaptive modes the audio master clock (MCLK) must be generated by the device and
continuously adjusted to track the host. It cannot be taken from a fixed-frequency oscillator, or from
an external codec acting as clock master. ``lib_xua`` measures the local MCLK and uses the result to
steer one of the following clock sources:

* **xcore.ai secondary PLL** (``XUA_USE_SW_PLL=1``). The on-chip secondary (or "application") PLL
  generates MCLK, and `lib_sw_pll <https://www.xmos.com/file/lib_sw_pll>`__ fine-tunes its frequency
  with a sigma-delta modulator running in a dedicated thread. Supported in synchronous and adaptive modes.
* **External Cirrus Logic CS2100** (``XUA_USE_SW_PLL=0``). The `xcore` drives a reference signal to
  the CS2100, which multiplies it up to MCLK. Supported in synchronous mode only.

The MCLK must be connected back into the `xcore` so that it can be counted (the MCLK count port), as
for asynchronous mode.

The measurement differs between the two modes:

* **Synchronous mode** locks MCLK to the USB SOF rate. When using the secondary PLL, the MCLK count is
  compared with the expected count every 10 ms of SOFs and the error is passed to ``lib_sw_pll``.
  When using a CS2100, the reference signal is toggled from SOFs.
* **Adaptive mode** locks MCLK to the rate at which the host sends samples. The number of complete
  sample frames received in playback (OUT) packets is counted and compared with the MCLK count over
  16 ms windows; the error is passed to ``lib_sw_pll``. Windows with no playback, or where the stream
  stopped or packets were lost part way through, leave the PLL at its previous setting. Adaptive mode
  requires the secondary PLL; it is not supported with a CS2100, and the master clock must be
  22.5792 MHz (``MCLK_441``) and 24.576 MHz (``MCLK_48``).

In both modes the recovered MCLK clocks the whole audio subsystem (I2S/TDM, etc.).

Adaptive mode endpoints
-----------------------

Adaptive mode applies to host-to-device playback only. The device-to-host recording endpoint remains
asynchronous: hosts, including the Windows USB Audio 2.0 class driver, treat adaptive recording streams
as asynchronous anyway (see the `Windows USB Audio 2.0 driver documentation
<https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/usb-2-0-audio-drivers>`_).
Recording packet sizes are calculated from the measured MCLK rate, as in asynchronous mode.

No feedback endpoint is used in adaptive mode, so ``UAC_FORCE_FEEDBACK_EP`` has no effect.
``XUA_FB_USE_REF_CLOCK`` is not supported in adaptive mode, because the reference clock cannot follow
adjustments to the secondary PLL; enabling it causes a build error.

Select adaptive operation in the application configuration with::

    #define XUA_SYNCMODE XUA_SYNCMODE_ADAPT
    #define XUA_USE_SW_PLL 1

CS2100 reference signal
-----------------------

When using a CS2100 in synchronous mode, the programmer should ensure the defines in
:numref:`opt_sync_ref_defines` are set appropriately.

.. _opt_sync_ref_defines:

.. list-table:: Reference clock location
   :header-rows: 1
   :widths: 25 60 20

   * - Define
     - Description
     - Default
   * - ``XUA_PLL_REF_TILE_NUM``
     - Tile location of reference to CS2100 device
     - Derived from PORT_PLL_REF in the application XN file.

The codebase expects the CS2100 reference signal port to be defined in the application XN file as
``PORT_PLL_REF``. This may be a port of any bit-width, however, connection to bit[0] is assumed::

    <Port Location="XS1_PORT_1A"  Name="PORT_PLL_REF"/>

Configuration of the external CS2100 device (typically via I2C) is beyond the scope of this document.
